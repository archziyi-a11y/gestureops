# 销售助手：运行与排查工作面

> 2026-11-10 修订：以下为历史调查提案，不再按该布局实现。故障和任务观测留在仪表盘详情；本工作面提供连接配置与基础修复；复杂问题通过总览拖动卡片组装上下文。当前实现见 [模型连接管理](MODEL-CONNECTIONS-20261110.md)。

日期：2026-11-09，Asia/Shanghai。状态：代码调查后的设计建议，尚未实现。本轮不调用生产诊断、不启动模型请求、不修改运行配置。

## 1. 核心职责

回答三个问题：哪里出了问题，影响哪些实际业务，现在怎么恢复。

仪表盘负责扫一眼发现异常；运行与排查负责展开同一异常、定位原因并进入正确处理入口。它不是另一个设备后台、知识管理页或部署控制台，也不是让员工先填写技术问题才能看到状态的工单页。

## 2. 现有代码能提供什么

| 来源 | 已有能力 | 不能直接推断的结论 |
| --- | --- | --- |
| `src/ui/sales-operations.js` 的 runtime 分支 | 记录排查对象、账号、问题描述，准备本地交接任务 | 当前页面没有真实运行观测 |
| `sales_http.py`：`/_health/live` | 应用路由可响应 | 上游、模型和业务链正常 |
| `sales_http.py`：`/sales/health` | 鉴权后查询账号，返回服务启动时间及配置字段 | `generation_available=true` 为固定返回；`model_configured` 不证明模型调用成功 |
| `sales_service.py`：`authorized_accounts` | 使用缓存或访问方舟账号接口 | `/sales/health` 不是纯本机进程检查，可能触发上游查询 |
| `sales_generation.py`：任务状态与错误 | profile、帮我回、润色、销售指导任务有排队、运行、成功、失败及时间记录 | 当前接口不是管理员任务清单；任务结果也不等于员工已使用 |
| `sales_http.py`：`/sales/jobs/{job_id}` | 限账号和客户的单任务查询 | 接口附带业务结果与画像，不宜直接作为全局监控列表 |
| `sales_generation.py`：清理及过期规则 | 已结束任务超过一小时可过期，并在后续提交时清理 | 不能直接承诺最近 24 小时完整统计 |
| 请求元数据、自动任务脚本 | 可作为进一步定位线索 | 本地脚本存在不证明服务器安装、启用或运行成功 |

后端路径均在 `project/modules/marketing-chat-insight/src/mktci/`。本次核对的是本地代码；线上实际可用字段和任务安装状态须在接入时验证，不能自动等同。`profile/ensure` 和 `draft` 会提交生成任务，不作为页面打开时的自动健康检查。

## 3. 页面建议：一个主列表，按需展开原因

### 顶部：正在影响使用的事

只显示有依据的当前异常，例如“回复生成连续失败”“画像更新任务中断”，同时说明受影响功能、范围和最近观测时间。没有采集数据时显示未取得观测；不能显示“全部正常”。历史故障已恢复则回到记录，不持续冒充当前告警。

### 主体：最近业务运行

用一个紧凑列表呈现功能、工作账号、请求时间、状态、耗时和失败原因；支持按功能、账号和失败状态筛选。默认聚焦需要处理的项，也能切回全部已有记录。

点击一项展开执行阶段、脱敏错误、相关版本和下一动作。不要默认展开客户聊天正文、画像全文或原始日志。账号与工作机分开标识，未建立关联时不猜测是哪台设备。

只有开始、结束时间齐全才给完成耗时；只有更新时间时不虚构阶段耗时。显示查询时间范围、观测时间和来源；界面统一北京时间，底层保留时区与服务端时间。

### 次级内容：依赖与自动任务

- 服务：应用是否响应、最近业务请求是否成功分别呈现。
- 方舟与模型：优先采用近期真实请求结果；配置存在、连接成功、生成成功不是同一事实。
- 画像与跟进：说明最近任务是否更新了业务产物，而非仅列缓存文件数量。进入具体问题后才核对对应账号与客户。
- 自动任务：实际启用状态、计划运行时间、最近开始和结束、结果及产出；尚未接入就不给合成“下一次运行”。仅纳入确实服务销售助手的任务。

正常依赖可收敛展示，异常展开。不要建设一面默认铺满端口、磁盘、日志和配置键的运维墙。

## 4. 与其他工作面划界

| 问题或目的 | 运行与排查做什么 | 原功能仍在哪里 |
| --- | --- | --- |
| 工作机无法使用或安装失败 | 显示影响和已知原因，定位到对应工作机 | 工作机：增加、停用、配置、上传 APK、批量更新 |
| 提示词版本错误、知识未命中 | 关联实际请求中的版本与来源，带问题进入调试 | 知识与物料：编辑、保存、对比、实装、回退、删除 |
| 团队物料无法读取 | 展示请求失败和受影响物料引用 | 团队物料：上传、改名、删除、上传者与内容维护 |
| 服务部署异常或需要搬迁 | 给出部署关联和诊断上下文 | 部署与迁移：目标、连接、部署、切换与回滚 |
| 画像未更新 | 定位该账号任务、时间和失败阶段 | 不另建画像浏览、分级编辑或客户管理系统 |
| 自动任务异常 | 核对真实调度、执行与产出，进入对应任务处理 | 共享任务只保留一个管理入口，不在每个项目重复配置 |
| 历史维护记录 | 关联引起故障或恢复的操作记录 | 维护记录：保存操作历史，不与业务请求混成一个列表 |
| 首页异常摘要 | 使用同一数据源与问题标识 | 仪表盘和资产卡：摘要，不再独立计算另一套健康结论 |

## 5. 实际使用体验

员工发现“帮我回没有结果”，进入运行与排查，页面自动读取已有观测。列表显示相关账号的失败请求；点开后看到“模型请求限流”及最近一次成功时间。有明确、可安全重试的接口时给对应操作，没有就提供已经组装证据的“复制排查任务”，不要求员工手填日志路径。

若问题其实是手机后台过旧，直接定位工作机页对应行；若是知识或提示词效果问题，带原问题和相关版本进入回答调试。返回排查页仍保留筛选与所选记录。

常规检查由页面完成；智能体处理需要跨系统定位和连续判断的故障。复制上下文不等于开始修复，也不把故障自动标为已解决。

## 6. 最小接入顺序与缺口

第一批先做“实际生成任务 -> 定位错误 -> 正确处理入口”，并提供只读应用存活观测。这比先堆服务健康灯更能回答员工问题。

需要补充管理员只读运行摘要与任务列表：分页、有界查询、脱敏账号与对象引用、状态和错误、实际可取得的时间与版本。不能把现有返回完整结果和画像的单任务接口直接批量暴露。若要跨天统计，另加不含正文的持久运行元数据及保留策略；未接入前只报告现有可查询范围。

第二批接入真实自动任务状态和产出核对。重试、暂停、重启等写操作逐项确认现有接口和幂等边界后再接，不放一个泛化的“一键修复”。页面只读刷新不自动触发模型、画像生成或批量重试。

接入验收覆盖：正常业务、模型限流、上游失败、排队与执行中、数据过期或未采集、页面刷新失败、已恢复故障。刷新失败保留上次结果并显示时间；执行结果未知先核对，不重复提交。最终证明用户能找到失败原因与处理入口，而非只有 HTTP 200 或测试数量。
